# Race Desk link adapters

R-02 adds a pure link builder for the existing tools. No separate R-02 brief was found; this bounded step follows the R-01 context contract and the request to continue after PR 392. Race identity remains in the existing registry. This does not add pages, navigation, child-application changes, source-pin changes, or a new registry schema.

## Decision and API

`buildToolLink(registry, input, target, options = {})` is exported from `scripts/race-desk/core/links.mjs`. It uses the R-01 `normalizeContext` contract: `input` identifies `raceId` and may contain `schemaVersion`, `sessionKind`, `openf1SessionKey`, and session-scoped `drivers`, each `{openf1SessionKey, driverNumber, lapNumber}`, with independent lap values. See [the context contract](race-desk-context.md) for validation and normalization. The supported targets are `tyres`, `grid`, `ghostcar`, and `telemetry`.

The result is `{status: "resolved", url}`, `{status: "missing", reason}`, or `{status: "unsupported", reason}`. Missing mappings and unsupported selections produce no URL. Invalid registry, context, target, or options throw `RegistryValidationError`. `options.currentYear` is required for Grid and Telemetry; every supplied year is an integer from 1950 through 2100. Supplying it explicitly makes the builder deterministic and lets it guard against the destination's date-dependent fallback. Other unknown options are invalid. No ambient clock, browser state, network, arbitrary origin or legacy host is used; query parameters are encoded with `URLSearchParams`.

Only Telemetry accepts the optional `telemetryCircuit` fact: `{season, openf1MeetingKey, circuitShortName, sourceId, reference, status: "verified"}`. The season and meeting must match the resolved registry race; `sourceId` must name an existing registry source, and the reference must identify the reviewed source field. The string must already be trimmed and match `/^[A-Za-z0-9 ._'-]{1,80}$/`. It is the OpenF1 `circuit_short_name`, not a circuit key, TYRES slug or venue name. Source and claim validation is structural: the builder does not read the referenced file or establish that the fact is true. A caller must review the exact source and its connection to the same meeting and season before marking the fact verified; an unsupported or unreviewed guess is not evidence.

## Target behavior

| Target | Required selection and mapping | Produced destination |
| --- | --- | --- |
| TYRES | Race only, with verified TYRES race ID and slug. Slug must be 1–40 lowercase ASCII letters, digits or hyphens. | `https://f1-stories.gr/tyres/{season}/{slug}/` |
| THE GRID | Race only, with verified `sourceKeys.jolpica: {season, round}`. Round 1–30 and season 2024 through `currentYear + 1`. | `/standings/?tab=drivers&embed=1&season=…&round=…` |
| Ghost Car | Verified OpenF1 meeting and session, 2–4 drivers, a concrete lap per driver. Independent laps are preserved. | `/ghostcar/?y=…&mk=…&sk=…&d1=…&l1=…&v=2`, with further driver/lap pairs and `nd` for 3–4 drivers. |
| Telemetry | Verified OpenF1 meeting and session, reviewed matching circuit fact, 1–4 drivers, and the same concrete lap for all drivers. Season must be 2023 through `currentYear`. | `/telemetry/?year=…&circuit=…&session=…&drivers=…&lap=…&tab=telemetry` |

Grid's destination is specifically its existing **embed view**: its historical round pin is applied there, while the ordinary full page does not initialize the same pin. TYRES and Grid cannot express a selected session, driver, or lap; the adapter returns unsupported rather than dropping it. Ghost Car requires two slots and uses the destination's v2 format. Telemetry has only one lap selector, so different per-driver laps are unsupported rather than silently collapsed. These checks avoid the destination defaults that can choose a different race, session or lap. A successful URL does not prove that remote session, driver or lap data exists or is complete.

The checked-in R-01 sample currently has no verified OpenF1 meeting or session keys. Ghost Car and Telemetry links for those records therefore return missing. Positive examples involving OpenF1 keys require clearly identified synthetic registry fixtures; synthetic keys must never be promoted to real source evidence.
